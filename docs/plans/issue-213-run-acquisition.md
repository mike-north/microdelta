# Run-scoped acquisition implementation choices for #213

This bounded implementation record sits under [RUN-011–RUN-014](../spec/operations.md) and [A-12a–c/f/g/i](../spec/acceptance.md). It applies to the existing direct operation path, not the later reusable source, shared rate coordinator or operator grant APIs.

An invocation of `Supervision.run` with operation ports mints one internal random run-instance identifier. It stays fixed across request passes, waits and lease reacquisition. The public/caller-supplied `runId` remains a correlation label subject to the facade's existing caller-uniqueness contract: callers must keep it unique per run because attribution and usage correlate by it. The private identifier isolates the retry tally defensively even if a caller violates that contract and repeats a public label; this does not make repeated labels supported attribution. Each actually sent attempt retains its public attribution and records the internal identifier. The current-run tally counts sent attempts bearing that identifier, not lifetime attempts or pass keys. A new invocation mints another identifier even under a repeated public label. Writer fencing, intent and stop gates retain send authority; the identifier grants none.

Operation journal format 2 adds nullable `runInstance` to attempts. Version-1 records remain readable: old attempts have absent internal instance and keep their exact IDs, statuses, attribution and usage. Rewriting a v1 record to v2 preserves those fields and marks historical attempts with null instance. A v2 record missing or malforming the field is integrity damage. A v1 run cannot remain live across this code upgrade, so old attempts cannot consume a newly invoked run's allowance. An allocated but unsent intent does not count; if its request-attempt ID is reused for an unconfirmed Accounting intent, public attribution remains stable while an actual later send is charged to its sending invocation. Legacy `resolved`/`abandoned` addresses and records remain readable and retain their existing behavior; no effect assertion becomes a data value.

The default is three **total sent attempts** per logical operation per run; positive finite `maxAttempts` overrides it. Rate attempts share this hard ceiling. The legacy `rateLimitRetries` field remains a **restrictive rate-only subcap** where applicable, never an extra pool or an override granting unknown/transient sends. Its old default 5 cannot raise the total ceiling of 3; explicit rate cap 1 cannot grant a new unknown attempt. Current declaration governs the current run; historical record fields remain readable as evidence.

For omitted direct-path timing, the first classified retry waits **2 seconds** and the second **4 seconds**. This bounded deterministic doubling is an initial delay for brief contention, not a provider-capacity claim or timing SLA. Explicit `backoffMilliseconds` retains its fixed-delay override, including zero. A known provider `retryAt` is a lower bound. Waiting spends no sent attempt, holds no network permit and cannot bypass stop.

An unknown/lost/rejected response may retry within this allowance without `safeToRepeat` or provider idempotency. An idempotency key, when requested, stays stable as a deduplication aid, not a charge guarantee. Exhausted unknown input remains unsettled/pending with truthful unknown usage; a later new run can try the same operation address. Known transient/rate exhaustion status and fold coverage are repaired by a subsequent issue, so this slice alone does not claim full #212 conformance.
