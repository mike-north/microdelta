# Resource reports implementation design

Issue [218](https://github.com/mike-north/microdelta/issues/218), implementing
[ACC-004/007/008](../spec/operations.md#acc-004--resource-state-reports-are-time-qualified-not-consumption)
and [A-14a–f](../spec/acceptance.md#resource-state-report-cases).

Accounting owns a separate versioned SQLite file for expiring reports, leaving the immutable additive schema unchanged. Explicit report intake is independent of a paid operation/usage intent. It accepts an environment and caller-supplied stable report id, observation epoch milliseconds, optional provider valid-until epoch milliseconds, nullable provider/service/account/pool/resource/unit/window identifiers, and nullable allowed/remaining quantities. Identifiers are opaque non-secret caller labels (not credentials). Amounts are nonnegative safe integers; zero is evidence, null unknown. No state summary or source ordering is computed.

Observation time is supplied once by intake's caller, not recomputed on redelivery. Future observation times are refused against injected Machine clock. Provider validity must be strictly later than observation. Omitted validity expires one hour after observation, optionally using a positive safe millisecond override supplied with the report. Provider validity takes precedence; output records provider/default/override basis. Expiry is exclusive: retained only while now < expiresAt. Time arithmetic must remain safe integers.

Identity is (environment, report). A retained identical canonical record is duplicate; different payload under that identity throws conflict. Duplicate never changes time or retention. After physical expiry removal there is no permanent identity tombstone (which would itself grow without bound): original unchanged redelivery is already expired and is refused; callers must never reuse an id or revise its original observation. This bounded identity horizon is explicit. Old reports and out-of-order arrivals remain separate evidence, with only deterministic identity ordering for query output.

Writable open validates/initializes only this dedicated schema and immediately deletes all expired reports. Every successful intake performs expiry maintenance in its transaction. Explicit maintenance deletes expiry <= clock time, for hosts that remain idle; an active writer automatically schedules the earlier of the next known expiry and a one-minute poll, using the injected Machine timer. Polling also notices reports added by another writer that has since closed. Storage failure is reported through the required owner callback and retried after one minute when the timer capability can allocate the retry; the retry is armed before notifying, and exceptions from the callback are contained, so a broken error observer cannot terminate maintenance or crash the timer turn. If retry allocation also fails, both errors are reported with observer exceptions contained; no future timer is claimed. Explicit maintenance, intake or reopen can restore cleanup after capability recovery. Persistent storage failure leaves rows stored until recovery and is not represented as successful eviction. Replacing a deadline preserves the prior timer until its replacement is armed. A post-commit scheduling-read failure is reported separately while the previous bounded poll remains active; it does not turn a successful durable write into a failed acknowledgment. Closing cancels the timer, and an already queued callback checks closure before touching storage. Timers do not keep an otherwise exited host alive. Reopen removes long-absent rows before returning. Queries filter expired rows but never evict. SQLite pages freed by deletion are reused; physical eviction means absent stored rows, not mandatory file truncation or secure erase.

Query opens through a separate Machine read-only SQLite capability exposing prepare/get/all/close only, never writable open. Missing files fail without creation. Unknown or empty schema fails without initialization. The report writer explicitly requests DELETE rollback journaling with FULL synchronous commits; existing Machine callers still default to WAL. Native WAL read-only open creates sidecars, so the inspection capability and DELETE writable open reject existing WAL files by reading their fixed header before SQLite opens them. Neither rejection changes an existing WAL database or sidecars. Rollback-journal inspection opens an existing file without journal/synchronous/schema assignments and makes no filesystem writes. Concurrent reads can see committed evidence while a writer handle stays open, but writer commit or exclusive-lock contention may produce a typed busy error after the existing bounded wait; this is not absent or zero evidence. Cooperative owners must keep the pathname and journal layout stable from header preflight through driver open and throughout handle lifetime; this preflight is not an atomic filesystem lock. A crashed hot rollback journal may require recovery through the writable owner before inspection succeeds; read-only inspection does not perform recovery writes. Schema/logical-store identity and exact object declarations are checked. Query selects one environment; separate file identity prevents accidental additive or foreign store use.

Acknowledgment is returned only after transaction success. Failures after callback completion have unknown durability (reuse AccountingDurabilityUnknownError). No dispatch/refresh/claim ports exist on this capability. Machine owns host reads, SQLite, and time only; Accounting owns schema, validity, identity, retention, and cleanup.
